Добавь в приложение «Учёт показателей НИР кафедры» журнал активности пользователей. Затем добавь в раздел «Отчёты» отчёт об активности: таблицу по пользователям, сгруппированным по категориям, за выбранный период с точностью до даты и времени. Отчёт смотрят в браузере и скачивают в формате DOCX.

## Контекст
Проект описан в README.md. Django 5.2, приложения в apps/.
- Раздел «Отчёты» — apps/reports:
  - реестр отчётов registry.py (ReportType с правилом доступа is_available);
  - первый отчёт — форма № 16: данные собираются в form16.py, страница и DOCX строятся из одного результата.
- Роли:
  - суперпользователь (администратор);
  - редакторы: is_staff, группа «Редакторы НИР»;
  - преподаватели, адъюнкты, курсанты: группы и карточки, get_person;
  - пользователь без карточки.
- Личный кабинет (apps/core/cabinet.py) ограничивает преподавателей, адъюнктов и курсантов белыми списками страниц. Новые страницы закрыты для них по умолчанию.
- Вход и выход — стандартные представления Django (login/logout). Пользователь загружается вместе с карточкой (apps/accounts/backends.py).
- Предметные данные изменяются через представления сайта и через админку.
- Есть точные проверки числа запросов (assertNumQueries) в нескольких тестах.

Соблюдай существующую структуру, стиль кода, оформление (Bootstrap 5, base.html) и русский интерфейс.

Перед началом проверь git status: незакоммиченные изменения сначала закоммить отдельным коммитом. Файлы, которые создал не ты (например, test_users.md), не трогай и не коммить.

## Главные принципы
1. Журнал пишется в одном месте и автоматически, а не вызовами в каждом представлении. Источники:
   - сигналы входа: user_logged_in, user_logged_out, user_login_failed;
   - middleware для запросов;
   - сигналы post_save и post_delete для изменений данных. Текущего пользователя передавай через contextvar, который выставляет middleware.
2. Журнал не должен ломать работу системы: ошибка записи в журнал не должна прерывать запрос пользователя. Логируй её через logging.
3. Пишется только то, что нужно для отчёта. Пароли, содержимое форм и значения полей не сохраняются.
4. Изменения, сделанные без пользователя (seed_demo, clear_data, миграции, shell), в журнал не попадают.

## 1. Модель журнала (новое приложение apps/activity)
ActivityLog:
- пользователь: FK на User, SET_NULL, необязательно; при неудачном входе пользователя может не быть;
- имя пользователя текстом: сохраняется на случай удаления пользователя и для неудачных входов;
- дата и время (индекс);
- действие:
  - «вход»;
  - «выход»;
  - «неудачный вход»;
  - «просмотр страницы»;
  - «добавление»;
  - «изменение»;
  - «удаление»;
  - «выгрузка отчёта» — скачивание DOCX;
- объект для добавления, изменения и удаления: тип (ContentType), id, краткое представление (str, до 200 символов);
- адрес запроса (path) и имя URL;
- IP-адрес. По умолчанию — REMOTE_ADDR. Заголовок X-Forwarded-For или X-Real-IP учитывай только при включённой настройке ACTIVITY_TRUST_PROXY_HEADER (в .env), иначе IP можно подделать. Опиши это в DEPLOY.md: при работе за Nginx настройку включают и передают заголовок.

Индексы: по дате, по пользователю и дате.

Что записывается:
- Просмотры страниц:
  - только успешные GET-запросы (код 200) к HTML-страницам вошедших пользователей;
  - без статики, медиа, админки и скачиваний.
- Изменения данных:
  - только для «главных» предметных моделей: Teacher, ResearchProject, Publication, IntellectualProperty, Conference, Report, ScientificSchool, DissertationDefense, Student, StudentAchievement, Adjunct, PlanStage, AdjunctAchievement, Task, TaskComment;
  - строки авторов и участников (PublicationAuthor и подобные) отдельными записями не пишутся, чтобы сохранение одной публикации не давало десятки записей;
  - список моделей задаётся в одном месте.
- Изменения через админку тоже попадают в журнал: там тот же пользователь в запросе.

Хранение:
- настройка ACTIVITY_LOG_DAYS (по умолчанию 365);
- команда manage.py purge_activity_log удаляет записи старше этого срока; есть параметр --days и вывод числа удалённых записей;
- в DEPLOY.md — пример запуска раз в сутки через cron или systemd timer.

Админка: журнал только для просмотра — без добавления и изменения; удаление разрешено только суперпользователю. Фильтры по действию, дате и пользователю, поиск по имени пользователя и адресу.

## 2. Отчёт «Активность пользователей»
- Добавь отчёт в реестр apps/reports/registry.py.
- Доступ: суперпользователь, а также пользователи с отдельным правом activity.view_activity_report. Право создай в модели (Meta.permissions) и выдавай вручную в админке. Редакторам по умолчанию его не выдавай.
- Для остальных страница отвечает 403. Страницу не добавляй в белые списки кабинета: преподавателям, адъюнктам и курсантам она закрыта и так.
- Адрес: /reports/activity/.

Параметры:
- период «с — по» с датой и временем (datetime-local). По умолчанию — последние 7 суток до текущего момента. Начало периода не может быть позже конца;
- категории пользователей для включения (по умолчанию все);
- флажок «Показывать пользователей без активности» (по умолчанию выключен).

Категории (определяются в одном месте, у каждого пользователя ровно одна, по приоритету):
1. Администраторы — суперпользователи.
2. Редакторы — is_staff.
3. Преподаватели — привязана карточка преподавателя.
4. Адъюнкты.
5. Курсанты.
6. Прочие пользователи — без карточки.
7. Неудачные входы с несуществующими логинами — отдельный блок, сгруппированный по введённому имени.

Таблица:
- блоки по категориям с заголовком и итоговой строкой по категории, внизу общий итог;
- столбцы:
  - пользователь (логин, ФИО);
  - входов;
  - неудачных входов;
  - просмотров страниц;
  - добавлено;
  - изменено;
  - удалено;
  - выгрузок отчётов;
  - первая и последняя активность в периоде;
- сортировка внутри категории — по последней активности, сначала недавние;
- логин ведёт на страницу подробного журнала пользователя за тот же период: /reports/activity/user/<id>/ (у неудачных входов без пользователя — по имени). Там хронологическая таблица: время, действие, объект, адрес, IP; фильтр по действию; постраничный вывод.

Реализация:
- данные отчёта собираются в одном месте (apps/reports/activity.py) агрегирующими запросами: Count с filter, Min, Max, группировка по пользователю;
- число запросов не зависит от числа пользователей и записей;
- время выводится в часовом поясе проекта (TIME_ZONE).

Выгрузка в DOCX:
- На странице отчёта кнопка «Скачать DOCX» выгружает сводную таблицу с теми же параметрами: период, категории, флажок пользователей без активности. Ответ — тот же URL с ?format=docx, как у формы 16. Подробный журнал пользователя выгружать не нужно.
- Документ строится из того же результата apps/reports/activity.py, что и страница. Данные для DOCX отдельно не собирай.
- Общие части оформления DOCX вынеси в общий модуль (например, apps/reports/docx_common.py) и используй их в обоих отчётах. Это шрифт Times New Roman, поля страницы, повтор строки заголовков таблицы, заполнение ячеек, объединённые строки разделов и формирование HTTP-ответа с именем файла (filename + filename* в UTF-8). Форма 16 после переноса должна выглядеть как раньше: её тесты проходят без изменений.
- Оформление:
  - A4, альбомная ориентация, потому что столбцов много;
  - Times New Roman: 12 пт в заголовке, 10 пт в таблице;
  - заголовок «Отчёт об активности пользователей», период «с ДД.ММ.ГГГГ ЧЧ:ММ по ДД.ММ.ГГГГ ЧЧ:ММ», выбранные категории;
  - таблица: строка заголовков повторяется на каждой странице; блоки категорий — объединённые строки на всю ширину; итоговые строки категорий и общий итог выделены полужирным;
  - ширина столбцов в сумме равна ширине текста страницы;
  - в конце — дата и время формирования и логин сформировавшего.
- Имя файла: «Активность_пользователей_ДД.ММ.ГГГГ-ДД.ММ.ГГГГ.docx»; ASCII-запасное имя — activity_ГГГГММДД-ГГГГММДД.docx.
- Скачивание этого отчёта тоже записывается в журнал как «выгрузка отчёта».
- Проверь документ визуально: сконвертируй его в PDF или PNG через LibreOffice (soffice --headless), если он установлен, и убедись, что таблица помещается на странице.

## 3. Влияние на систему
- Запись просмотра страницы — один INSERT на запрос. Тесты с assertNumQueries, где число запросов вырастет, исправь и перечисли в отчёте с объяснением.
- Выгрузку формы 16 в DOCX журнал отмечает как «выгрузка отчёта».
- Сам журнал не должен попадать в seed_demo и clear_data: проверь DOMAIN_MODELS. clear_data при этом очищает журнал: записи без пользователей бессмысленны, а ссылки на удалённых пользователей обнулятся.

## 4. Демо-данные
seed_demo создаёт правдоподобный журнал за последние 30 дней:
- входы и выходы демо-пользователей разных категорий;
- просмотры страниц;
- добавления и изменения записей — объекты реальные;
- несколько неудачных входов, в том числе с несуществующим логином.

Записи создаются напрямую, а не через сигналы. После seed_demo отчёт за последние 7 суток не должен быть пустым. seed_demo проверяй только на копии базы.

## 5. Тесты
- Вход, выход и неудачный вход пишутся. Неудачный вход с несуществующим логином сохраняет введённое имя, пароль не сохраняется.
- Просмотр страницы пишется. Статика, админка, ошибки 403/404, анонимные запросы и скачивание DOCX как просмотр не пишутся. Скачивание DOCX пишется как «выгрузка отчёта».
- Добавление, изменение, удаление публикации через сайт дают по одной записи на действие, без записей для авторов. Изменение через админку пишется.
- seed_demo и изменения без пользователя не пишутся.
- Ошибка записи журнала не ломает запрос (замокай сохранение и проверь ответ 200).
- IP: REMOTE_ADDR по умолчанию; заголовок прокси — только с ACTIVITY_TRUST_PROXY_HEADER.
- Отчёт:
  - категории и приоритет;
  - подсчёты и итоги;
  - фильтр периода по дате и времени (граничные записи);
  - фильтр категорий;
  - пользователи без активности по флажку;
  - неудачные входы с несуществующим логином;
  - подробный журнал пользователя.
- DOCX отчёта об активности:
  - ответ 200, правильный Content-Type и имя файла;
  - файл открывается python-docx;
  - в таблице есть блоки категорий, итоговые строки и нужные пользователи;
  - параметры периода и категорий применяются;
  - скачивание записано в журнал как «выгрузка отчёта»;
  - для пользователя без доступа — 403.
- Форма 16 после выноса общих частей DOCX: её тесты проходят без изменений.
- Доступ: суперпользователь и обладатель права — 200; редактор, преподаватель, адъюнкт, курсант — 403; анонимный — на вход. Отчёт показывается в списке /reports/ только тем, кому доступен.
- Число запросов отчёта не растёт с числом пользователей и записей.
- purge_activity_log удаляет только старые записи.
- clear_data очищает журнал.
- Все существующие тесты проходят.

## Чего НЕ делать
- Не вызывать запись журнала вручную в каждом представлении (кроме отметки выгрузки DOCX, если сигналом это не сделать).
- Не сохранять пароли, содержимое форм и значения полей.
- Не открывать отчёт редакторам, преподавателям, адъюнктам и курсантам без явно выданного права.
- Не добавлять новые зависимости.
- Не трогать данные в db.sqlite3: перед миграцией сделай резервную копию; seed_demo — только на копии базы.
