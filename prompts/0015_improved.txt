Настрой в приложении «Учёт показателей НИР кафедры» резервное копирование: команду создания копии базы данных, ротацию старых копий, проверку целостности и документацию по бэкапам.

## Контекст
Проект описан в README.md. Django 5.2, приложения в apps/, запуск команд — `uv run python manage.py <команда>`.
- База данных выбирается настройкой `DB_ENGINE` в config/settings.py: `sqlite` (по умолчанию; файл — `DB_NAME` или `db.sqlite3` в корне проекта) или `postgresql`. Команда должна работать в обоих режимах.
- Медиа-файлов и пользовательских загрузок в проекте нет (`MEDIA_*` не настроены): копировать нужно только базу данных и файл `.env` (в нём DJANGO_SECRET_KEY и пароль базы).
- Управляющие команды живут в `apps/<приложение>/management/commands/`: `create_admin` (apps/accounts), `seed_demo` и `clear_data` (apps/core), `purge_activity_log` (apps/activity) — по образцу последней сделана и регулярная задача с ротацией. Команда бэкапа логичнее всего в apps/core.
- Развёртывание — DEPLOY.md: сервер Ubuntu, приложение в `/opt/nir`, системный пользователь `nir`, Gunicorn + systemd + Nginx. Раздел 6 «Резервное копирование» уже содержит ручные команды (sqlite3 `.backup`, `pg_dump`, пример cron с `find -mtime +30 -delete`) — приведи его в соответствие с новой командой, противоречий быть не должно.
- Часовой пояс проекта — Europe/Moscow (TIME_ZONE).

Соблюдай существующую структуру и стиль кода команд (русские сообщения, вывод итогов в консоль, параметры через argparse add_arguments, как у purge_activity_log).

Перед началом проверь git status: незакоммиченные изменения сначала закоммить отдельным коммитом. Файлы, которые создал не ты (например, test_users.md), не трогай и не коммить.

## Главные принципы
1. Копия базы консистентна: файл `db.sqlite3` не копируется операционной системой (cp/rsync) при работающем сервере. SQLite — через Online Backup API (стандартный модуль sqlite3, `Connection.backup()`). PostgreSQL — через `pg_dump -Fc` (subprocess, пароль из настроек через окружение PGPASSWORD).
2. Путь к базе берётся из настроек соединения (`settings.DATABASES`), а не хардкодится: `DB_NAME` может указывать на другой файл.
3. Копия проверяемая: после создания SQLite-копии на ней выполняется `PRAGMA integrity_check`; при ошибке битая копия не остаётся, команда завершается ненулевым кодом, чтобы cron/systemd зафиксировали сбой.
4. Ротация — часть команды (параметр), а не внешний `find`: старые копии удаляет та же команда по дате в имени файла.
5. Никаких новых зависимостей: только стандартная библиотека Python и системный `pg_dump`.

## 1. Команда `backup`
`uv run python manage.py backup` создаёт в каталоге копий:
- копию базы: `db-ГГГГ-ММ-ДД.sqlite3` (SQLite) или `nir-ГГГГ-ММ-ДД.dump` (PostgreSQL) — имена как в действующем DEPLOY.md;
- копию `.env` рядом: `env-ГГГГ-ММ-ДД` с правами 600.

Требования:
- параметры: `--output-dir <каталог>` (по умолчанию — `backups/` в корне проекта; каталог создаётся, если его нет) и `--keep <дней>` (ротация, по умолчанию 30). Другие параметры добавляй только при необходимости и объясни.
- повторный запуск в тот же день не должен падать с ошибкой «файл существует»: либо перезапись, либо время в имени — выбери вариант и объясни.
- в конце — вывод: путь и размер созданных файлов, сколько старых копий удалено ротацией.
- код выхода: 0 при успехе, ненулевой при любой ошибке (не удалось создать или проверить копию).
- добавь `backups/` в .gitignore: копии базы и `.env` не должны попадать в git (каталог может находиться вне репозитория — тогда убедись, что и там они не коммитятся).

## 2. Ротация
- `--keep N` удаляет копии базы и `.env` старше N дней по дате в имени файла. Свежие и непохожие на копии файлы не трогай.
- В DEPLOY.md замени пример cron с `find` на запуск команды с ротацией: ежедневно (например, в 03:00) от пользователя `nir`, вывод — в лог (по образцу раздела 3.8). Покажи вариант и через cron, и через systemd timer — выбери основной и объясни, второй упомяни кратко.

## 3. Проверка целостности
- SQLite: после создания копии открой её отдельным соединением и выполни `PRAGMA integrity_check`. Ошибка или результат не `ok` — удалить копию, сообщение в stderr, ненулевой код выхода.
- Для PostgreSQL pg_dump копия консистентна сама по себе; integrity_check не требуется. Проверка восстановления описывается в документации (раздел 4).

## 4. Восстановление
Восстановление — ручная процедура, команда её не выполняет. Зафиксируй в DEPLOY.md пошагово для обоих движков:
- остановить сервис (`sudo systemctl stop nir`);
- SQLite: скопировать выбранную копию на место файла базы; PostgreSQL: `pg_restore --clean` в базу;
- запустить сервис, проверить вход в систему.

## 5. Тесты
- На SQLite: команда создаёт копию; копия открывается отдельным соединением и содержит актуальные данные (создай запись, сделай копию, проверь её наличие в копии).
- `integrity_check` выполняется; имитируй сбой проверки — копия не остаётся, код выхода ненулевой.
- Повторный запуск в тот же день не падает (поведение — как выбрано в п. 1).
- Ротация: `--keep` удаляет только просроченные копии (подготовь файлы с нужными датами в имени), свежие не трогает; копия `.env` создаётся с правами 600.
- Путь базы из `DB_NAME`: с временным файлом базы копия создаётся из него.
- PostgreSQL-ветка: если `pg_dump` недоступен — тест пропускается (skip); если доступен или замокан — проверь, что subprocess вызывается с корректными параметрами (имя базы, пользователь, хост, формат custom).
- Все существующие тесты проходят.

## 6. Документация
- DEPLOY.md, раздел 6 «Резервное копирование»:
  - что входит в копию (база + `.env`) и где она лежит;
  - создание вручную и по расписанию (cron/timer, лог, код выхода для фиксации сбоев);
  - ротация (`--keep`);
  - восстановление для SQLite и PostgreSQL;
  - напоминание: копии и копии `.env` — секретные данные, в git их не коммитят, хранят также за пределами сервера.
- README: краткий абзац о бэкапе со ссылкой на DEPLOY.md и строка о команде в структуре проекта.
- .env.example: если введёшь настройки — с комментариями; по возможности обойдись параметрами команды.

## Чего НЕ делать
- Не копировать `db.sqlite3` через cp/rsync/File.copy при работающем сервере.
- Не добавлять зависимости (django-dbbackup и т. п.) и не тащить облачные загрузки, шифрование, дедупликацию — простая команда + документация.
- Не коммитить каталог копий и копии `.env`.
- Не бэкапить `staticfiles/`, `.venv/`, `db.sqlite3-wal/journal`: статика пересобирается collectstatic, окружение — uv pip sync.
- Не восстанавливать копии поверх рабочей базы автоматически: восстановление — только ручная процедура из DEPLOY.md. seed_demo и проверка восстановления — только на копии базы.
- Не трогать данные в db.sqlite3 разработки.

## Результат
- Запусти команду (на копии базы или так, чтобы рабочая база разработки не пострадала), убедись, что копия создаётся и проверка целостности проходит; прогони все тесты.
- Сделай коммит с осмысленным сообщением (без push).
- Кратко перечисли:
  - команду, её параметры и формат имён копий;
  - поведение ротации и проверки целостности;
  - изменения в DEPLOY.md и README;
  - изменённые файлы.
- Отдельно назови решения, которые ты принял сам (повторный запуск в тот же день, способ расписания, место команды), и отличия от промпта.
